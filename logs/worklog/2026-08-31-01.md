## 왜 이렇게 했나
<!-- 다른 선택지가 있었다면 왜 그걸 안 골랐는지. 3개월 뒤의 내가 읽습니다. -->

- **PR을 만들지 않기로 했다.** 혼자 하는 프로젝트라 리뷰어가 없고, PR의 "변경 이력" 역할은
  이 작업일지 체계가 이미 하고 있다. 게다가 당시 저장소에 브랜치가 하나뿐이라
  합칠 대상(base)이 없어서 PR 자체가 성립하지 않았다.
  → 팀원이 생기거나, CI를 걸어 통과해야만 합치게 하고 싶어지면 그때 도입한다.
- **`hello.py` 의 에러 메시지를 길게 쓴 이유**: 초보자가 처음 막히는 지점이 전부 키 관련이다.
  "키 없음 / 예시값 그대로 / 형식 이상" 을 각각 구분해서 다음에 뭘 해야 하는지까지 출력하게 했다.
  `KeyError` 나 401 스택트레이스만 뜨면 거기서 하루가 날아간다.
- **실제 API 호출은 하지 않았다.** 원격 컨테이너에서 호출해봤자 로컬 키가 유효한지는
  증명되지 않고, 비용만 발생한다. 검증은 로컬에서 사용자가 직접 해야 의미가 있다.


## 막힌 점 / 배운 점
<!-- 에러 메시지 원문, 삽질한 시간, 해결한 방법. 여기가 이 일지에서 제일 값어치 있는 칸입니다. -->

- **자동 일지 훅에 버그가 있었다. 어제 만든 게 실제로는 한 번도 안 걸렸다.**
  매칭 패턴이 `*"git commit"*` 이라 **붙어있는 글자** 만 찾았는데,
  실제 실행한 명령은 `git -c user.name=... commit` 이라 중간에 옵션이 끼어서 안 잡혔다.
  어제 테스트할 때 `git commit -m msg` 라는 단순한 형태로만 넣어봐서 통과한 것처럼 보였던 것.
  → `*git*commit*` 으로 느슨하게 바꿔 해결. 오탐이 늘어도 해시 중복검사가 걸러준다.
  → **교훈: 훅 테스트는 "실제로 쓰는 명령어 그대로" 넣어야 한다.** 단순화한 입력으로 통과한 건
     통과한 게 아니다.
- **원격 브랜치 삭제는 이 세션 권한으로 불가능하다.** `git push origin --delete` 가 HTTP 403.
  프록시 문제인가 확인했지만 `recentRelayFailures: []` 로 정상이었고, GitHub MCP 도구에도
  브랜치 삭제 기능 자체가 없었다(create/list만 있음). 결국 사용자가 웹 UI에서 직접 삭제.
  → 이 세션의 git 자격증명은 push는 되고 delete는 안 되는 범위다.
- **GitHub Branches 화면의 "Your branches" 와 "Active branches" 는 겹치는 분류다.**
  같은 브랜치가 두 줄로 보여서 브랜치가 2개인 줄 알기 쉽다. `All` 탭에서 보면 중복 없이 나온다.
- **pip 설치가 한 번 타임아웃 났다** (`files.pythonhosted.org ... Read timed out`).
  `--timeout 120 --retries 5` 로 재시도해서 해결. 네트워크 일시 문제였고 코드 문제가 아니었다.
