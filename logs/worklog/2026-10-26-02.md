## 왜 이렇게 했나
<!-- 다른 선택지가 있었다면 왜 그걸 안 골랐는지. 3개월 뒤의 내가 읽습니다. -->

**왜 절차를 이 저장소에 다시 적었나.** `link` 에 이미 있는데 복사한 이유는,
툰 계정은 **저장소·계정·토큰이 다 다르기** 때문이다. 핫딜 문서를 보면서 머릿속으로
바꿔 읽어야 하면 또 틀린다. 특히 Secret 을 `link` 에 넣으면 핫딜이 고장나는데,
그건 문서가 핫딜 기준일 때 제일 일어나기 쉬운 사고다.

**왜 "앱이 저장소와 연동된다"를 바로잡았나.** 사용자가 "link랑 연동된 오늘의 할인"
이라고 표현했는데, 실제로 앱은 GitHub 저장소를 전혀 모른다. 앱이 묶이는 건
**스레드 계정**이고, 저장소에는 토큰을 복사해 넣을 뿐이다. 이 모델을 잘못 알면
앱을 몇 개 만들어야 하는지, 토큰을 어디 넣어야 하는지가 계속 헷갈린다.



## 막힌 점 / 배운 점
<!-- 에러 메시지 원문, 삽질한 시간, 해결한 방법. 여기가 이 일지에서 제일 값어치 있는 칸입니다. -->

**1. 내 설명이 너무 어려웠다. 이게 이번 세션 제일 큰 실패다.**
사용자가 `?????????????  나 너 말 너무 어려워` 라고 했다.
앱/저장소 연결 관계를 도식과 표로 설명했는데, 정작 사용자는 **"토큰이 뭔지"**
부터 모르는 상태였다. 용어를 그대로 쓰면서 구조부터 설명한 게 틀렸다.
→ 다시 쓴 방식: **토큰 = 비밀번호 같은 글자 / 앱 = 그 글자를 만드는 기계 /
저장소 = 글자를 보관하는 곳.** 그리고 전체를 한 번에 주지 않고
"①번만 해보고 알려주세요" 로 쪼갰다.
→ `CLAUDE.md` 규칙 7(작업자는 초보자다)을 지켰다고 생각했는데,
**명령어만 복붙 가능하게 주는 게 규칙 7 이 아니다.** 용어부터 풀어야 한다.

**2. `link` 코드를 읽고 보니 내 리포트의 병목 3개가 이미 풀려 있었다.**
- 이미지 공개 URL → 저장소 `images/` 에 커밋해서 `raw.githubusercontent.com` 주소를 만든다
- 루틴이 승인을 기다릴 수 없는 문제 → **GitHub 이슈 제목이 상태 저장소**다
  (`초안` → 제목을 `예약` 으로 고치면 승인)
- 네트워크 정책 → Actions
→ 배운 것: **코드를 안 읽고 리포트를 썼다.** `link` 쪽이 이미 해결한 문제를
병목으로 올려서 사용자 결정을 어렵게 만들었다. 같은 조직 안의 다른 저장소를
먼저 읽어봤어야 했다.

**3. 툰 계정에 그대로 못 쓰는 것 2개를 찾았다.**
- `.gitignore` 18행 `content/*/out/` 때문에 **합성 결과물이 커밋되지 않는다.**
  그러면 `raw.githubusercontent.com` 공개 URL 을 만들 수 없다. **아직 안 고쳤다.**
- 핫딜은 이슈 본문에 이미지를 붙이지만, 툰은 `compose.py` 가 저장소 안에 PNG 를 만든다.
  이슈 본문 생성 방식이 달라져야 한다.

**4. 글자 수는 문제없었다.** 콘티 3건 전부 캡션+고지+해시태그 합쳐 289~305자.
스레드 500자 제한에 여유가 있다.

**5. 권한 하나가 빠지면 수익이 0이 된다.** `threads_manage_replies` 가 없으면
툰은 올라가는데 **첫 댓글 링크가 안 달린다.** 문서에 굵게 표시해뒀다.
